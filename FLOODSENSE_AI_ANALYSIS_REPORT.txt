1. EXECUTIVE SUMMARY
--------------------------------------------------------------------------------
FloodSense AI is an early-warning web platform and predictive engine designed to
forecast hyperlocal urban flooding across vulnerable flood hotspots and
underpasses in Bengaluru, Karnataka, India.

Urban flooding in Bengaluru is characterized by severe spatial heterogeneity:
low-lying valleys, historical lake beds (e.g., Bellandur), railway underpasses,
and congested stormwater drainage networks (Rajakaluves) flood rapidly during
high-intensity precipitation, often while adjacent neighborhoods remain dry.

The project currently implements a functional "Vertical Slice 1" featuring:
  - An explainable, physics-inspired risk calculation engine.
  - A FastAPI backend exposing REST APIs for risk scoring and spot metadata.
  - A React 18 + TypeScript + Vite frontend with Leaflet interactive mapping.
  - Dynamic simulation controls (precipitation sliders for current and forecast rain).
  - A data preparation pipeline designed to correlate historical Open-Meteo
    hourly rainfall with crowdsourced/sourced flood incidents.
  - Unit and integration test suites validating physics invariants and data logic.

4. HYDROLOGICAL RISK ENGINE & METHODOLOGY
--------------------------------------------------------------------------------
The backend implements a transparent, explainable physical baseline model in
`backend/app/services/risk_engine.py`. Rather than relying on an opaque "black-box"
model during the prototype stage, every factor is deterministically calculated.

4.1 Effective Rainfall Intensity:
---------------------------------
Precipitation is aggregated into an effective intensity metric (mm/h) using a
decayed combination of immediate rain, recent antecedent rain, and forecast rain:

  Effective Intensity (mm/h) = 0.5 * rain_1h_mm
                             + 0.3 * (rain_3h_mm / 3)
                             + 0.2 * (forecast_2h_mm / 2)

4.2 Topographical & Infrastructure Susceptibility:
--------------------------------------------------
Each location is assigned an intrinsic susceptibility score (0.0 to 1.0) based
on four calibrated factors:
  - Depression Depth   (Weight: 35%, Max Cap: 6.0 m)   : Sits below surrounding terrain
  - Catchment Area     (Weight: 25%, Max Cap: 300.0 ha): Upstream drainage watershed
  - Drain Distance     (Weight: 20%, Max Cap: 400.0 m) : Proximity to stormwater drain
  - Incident History   (Weight: 20%, Max Cap: 5 events): Past documented floods

  Susceptibility = 0.35 * clamp(depth / 6.0)
                 + 0.25 * clamp(catchment / 300.0)
                 + 0.20 * clamp(drain_dist / 400.0)
                 + 0.20 * clamp(incidents / 5.0)

4.3 Composite Risk Score:
-------------------------
The final risk score combines rainfall intensity and intrinsic susceptibility:

  Rain Factor = clamp(Effective Intensity / 50.0 mm/h) ^ 0.8
  Risk Score  = clamp(Rain Factor * (0.35 + 0.9 * Susceptibility), 0.0, 1.0)

4.4 Classification Thresholds & Warning Levels:
-----------------------------------------------
  - GREEN ("Low risk")        : Risk < 0.35
  - AMBER ("Watch")           : 0.35 <= Risk < 0.65
  - RED   ("Likely to flood") : Risk >= 0.65

4.5 Lead Time Calculation:
--------------------------
To determine actionable lead time:
  1. The risk score is evaluated using current rainfall only (forecast = 0).
  2. If the inclusion of the 2-hour forecast elevates the alert level
     (e.g., from Green to Amber, or Amber to Red), a warning lead time of
     approximately 45 minutes is triggered (`FORECAST_LEAD_MIN = 45`).
  3. If the spot is already at that level under current rainfall, lead time is 0 min.
  4. If the spot remains Green, lead time is null.

4.6 Human-Explainable Risk Drivers:
-----------------------------------
The engine automatically populates driver annotations explaining the underlying
cause of elevated risk, such as:
  - "Heavy rain (about 38 mm/h effective)"
  - "Sits 4.5 m below its surroundings"
  - "Large upstream catchment (260 ha)"
  - "Nearest drain is 320 m away"
  - "4 past flood reports"

6. DATA PIPELINE & PROVENANCE
--------------------------------------------------------------------------------
The project features an automated data ingestion and labeling framework in
`backend/scripts/prepare_data.py`:

  - Historical Rainfall Ingestion:
    Fetches hourly precipitation from the Open-Meteo Historical Weather Archive
    API for every study coordinate in annual partitions, cached locally under
    `data/raw/rainfall/{spot_id}_{start}_{end}.json`.
  - Feature Engineering:
    Constructs rolling time-series features (`rain_1h_mm`, `rain_3h_mm`,
    `rain_24h_mm`, and future lookahead `next_2h_mm`).
  - Label Generation:
    Matches reported events in `incidents.csv` to time windows.
    - Positive labels (`flood = 1`): Spot-hours within +/- 1 hour of reported time
      (or peak rain hour if clock time was unrecorded).
    - Ambiguity buffer: Hours within +/- 3 hours of a flood window are excluded.
    - Negative labels (`flood = 0`): Rainy hours with >= 5 mm rain in previous 3 h,
      ensuring negatives represent true non-flooding rain events rather than dry days.
  - Manifest Tracking:
    `data/manifests/dataset_manifest.json` tracks source URLs, coordinate
    sampling boundaries, licensing terms, and SHA-256 file checksums.


7. FRONTEND USER EXPERIENCE & INTERFACE
--------------------------------------------------------------------------------
The user interface is built as a split-pane single-page application:

  - Left Control & Overview Sidebar (360px):
    - Header with title and tagline.
    - Interactive Dual Range Sliders:
      * Current rainfall rate: 0 to 80 mm/h.
      * Forecast 2-hour accumulation: 0 to 150 mm.
      * 150ms debounce prevents unnecessary API thrashing.
    - Dynamic status banner summarizing the total number of critical locations.
    - Ranked spot list displaying status dot (Green/Amber/Red), location name,
      alert classification, lead time, and risk percentage.
  - Right Interactive Map Canvas:
    - Built on Leaflet and OpenStreetMap tiles.
    - Centered on Bengaluru [12.96, 77.64] at zoom level 12.
    - Risk markers dynamically change radius (9px to 23px) and fill color
      (#2e7d5b green, #d9962b amber, #c23b2e red) based on calculated risk.
    - Bidirectional selection: Clicking a spot on the list or on a map marker
      triggers a smooth zoom/pan ("flyTo") and displays an interactive popup
      containing the full risk breakdown and causative drivers.
  - Responsive Styling:
    - Automatic adaptation for mobile viewports (< 800px) switching from
      horizontal split to vertical stacked layout (55% map, 45% controls).

9. CURRENT LIMITATIONS & GAP ANALYSIS
--------------------------------------------------------------------------------
1. Estimated Spot Parameters (Fixtures):
   Terrain elevation depth (`rel_depth_m`), catchment area (`catchment_ha`),
   and drain distances (`drain_dist_m`) in `fixtures.py` are heuristic estimates.
   They need to be derived from real SRTM/Copernicus 30m DEM raster grids and
   OSM waterway / stormwater drain shapefiles.

2. Empty Incident Log:
   `data/raw/incidents.csv` contains only column headers. A minimum of 20+ verified
   flood events (e.g., September 2022 Bengaluru floods, May 2023 underpass drownings)
   must be populated to train or benchmark ML models.

3. Frontend 3h Rain Approximation:
   In `frontend/src/App.tsx`, `rain_3h_mm` is hardcoded as `rainNow * 2` rather than
   integrating a third slider or fetching live cumulative historical rain.

4. Absence of Live Weather Ingestion:
   The application is currently driven exclusively by manual simulation sliders.
   It lacks an automated live ingestion service polling IMD (India Meteorological
   Department) radar/AWS or Open-Meteo current forecast APIs.

5. AI / LLM Agent Not Yet Integrated:
   While the repository is named `floodsense-ai` and contains `.env.example` with
   an `OPENROUTER_API_KEY`, the agentic reasoning layer (e.g., automated municipal
   response generation, emergency routing alerts, citizen multilingual alerts)
   is not yet implemented.

6. Security & Production Hardening:
   - CORS is restricted to `localhost:5173`.
   - No rate limiting or API authentication.
   - Missing Docker containerization and reverse proxy (Nginx / Caddy) configuration.
